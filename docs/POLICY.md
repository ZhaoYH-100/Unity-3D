# 资料库管理规范

> 用途：实施方案 · 读者：项目负责人、文档生成者、开发与测试人员
> 版本：1.0 · 状态：active · 负责人：项目开发负责人
> 实施对象：`docs/` 与 `tools/doclib.py`

## 1. 目标与契约

### 1.1 要解决的问题

AI 和开发过程会持续产生方案、设计、测试记录与交付文档。若仅按文件名堆放，容易出现同一主题多个版本、无法判断哪份现行、生成来源丢失、正文被静默覆盖以及索引与实体不一致。本体系用稳定 ID、结构化元数据、受控状态机、修订快照和可重复校验解决这些问题。

### 1.2 适用范围

适用于本仓库内需要长期保留和追溯的 Markdown、TXT、JSON、CSV、PDF、DOCX 等项目资料。临时草稿和不具备长期价值的终端输出不要求入库。

明确不做：在线协同编辑、用户权限、自动事实核验、OCR、附件流程、文档内容评分、正式签署审批。

### 1.3 关键质量属性

| 质量属性 | 可观察场景 | 阈值 | 当前证据 |
| --- | --- | --- | --- |
| 完整性 | 对当前资料库运行 `validate` | 0 个契约错误；索引与元数据一致 | B（实现与自动化测试） |
| 可追溯性 | 查看任一 AI 资料 | 100% 记录来源类型、生成工具、模型版本、Prompt 引用和核验状态 | B（结构约束与测试） |
| 一致性 | 修改状态或修订后不手工重建 | `catalog.json`、`INDEX.md` 与元数据在一次命令内同步 | B（命令后校验） |
| 可恢复性 | 误归档或索引损坏 | 正文不删除；旧修订保留；索引可从元数据重建 | B（实现与测试） |
| 可用性 | 1,000 份资料规模内执行元数据/文本检索 | 单次检索不超过 2 秒；结果包含 ID、状态和摘要 | D（性能阈值待基准测试） |

## 2. 术语与状态

| 术语 | 含义 |
| --- | --- |
| 条目 | 一个稳定 ID 对应的一级资料目录 |
| 主文件 | `primaryFile` 指向的当前正文 |
| 修订 | 同一稳定 ID 下经 `revise` 登记的新正文；旧正文进入 `versions/` |
| 替代 | 新建一份独立资料，并用 `supersededBy` / `supersedes` 建立双向关系 |
| 资料域 | 按主要归属划分的目录：project、requirements、unity、backend、web、qa、delivery、research、general |

| 状态 | 含义 | 生成或运行时处理 |
| --- | --- | --- |
| `draft` | 草稿，内容可能不完整 | 可修订；不得作为项目事实或实施依据 |
| `review` | 等待评审或人工核验 | 可展示；不得自动进入现行依据集 |
| `active` | 已批准的现行资料 | 可进入实施、问答和后续生成上下文 |
| `superseded` | 已被另一份 active 资料替代 | 默认只用于追溯，不进入现行依据集 |
| `archived` | 已归档 | 默认不出现在列表与检索中；不物理删除 |

状态机：

| 当前状态 | 合法事件 | 下一状态 | 守卫与副作用 |
| --- | --- | --- | --- |
| `draft` | 提交评审 | `review` | 操作人必填；记录历史 |
| `draft` | 归档 | `archived` | 操作人必填；保留正文 |
| `review` | 退回修改 | `draft` | 记录历史 |
| `review` | 批准 | `active` | AI 资料必须填写人工核验说明并标记 `reviewed` |
| `review` | 归档 | `archived` | 记录历史 |
| `active` | 建立替代 | `superseded` | 替代资料必须 active；双向关联；操作人和说明必填 |
| `active` | 归档 | `archived` | 记录历史 |
| `superseded` | 归档 | `archived` | 记录历史 |
| `archived` | 任何状态变更 | 不允许 | 资料完整保留；不得原位恢复 |

## 3. 数据契约

每个条目必须包含 `meta.json`。核心字段：

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `schemaVersion` | integer | 是 | 当前为 `1` |
| `id` | string | 是 | `DOC-YYYYMMDD-NNN`，全局唯一且稳定 |
| `title` | string | 是 | 非空 |
| `type` | enum | 是 | 见脚本 `DOC_TYPES` |
| `domain` | enum | 是 | 见脚本 `DOMAINS` |
| `status` | enum | 是 | draft/review/active/superseded/archived |
| `version` | string | 是 | 业务版本；不得替代 `revision` |
| `revision` | integer | 是 | 从 1 开始，每次 `revise` 加 1 |
| `owner` | string | 是 | 当前内容负责人 |
| `createdAt` / `updatedAt` | string | 是 | 带时区 ISO 8601 |
| `summary` | string | 是 | 可为空；应写查询所需的主题摘要 |
| `tags` | string[] | 是 | 大小写去重后的检索标签 |
| `primaryFile` | string | 是 | 相对条目目录的安全路径 |
| `file` | object | 是 | 路径、SHA-256、大小和媒体类型 |
| `provenance` | object | 是 | 来源、生成工具、模型、Prompt 引用与人工核验 |
| `related` | string[] | 是 | 已存在的资料 ID，不得自引用 |
| `supersedes` / `supersededBy` | string/null | 是 | 替代关系，必须双向一致 |
| `versions` | object[] | 是 | 旧修订快照 |
| `history` | object[] | 是 | 不得为空；最后事件状态等于当前状态 |

`provenance.humanReview` 取值：

| 值 | 含义 | 使用规则 |
| --- | --- | --- |
| `pending` | 尚未人工核验 | AI 资料允许处于 draft/review |
| `reviewed` | 已完成人工核验 | AI 资料进入 active 的必需条件；`reviewNotes` 必须非空 |
| `not-required` | 无需 AI 核验 | 用于人工、导入或非 AI 资料 |

## 4. 不变量

以下条件必须始终成立：

1. 同一资料 ID 只有一份活动条目，目录名与元数据 ID 完全一致。
2. 已入库文件的 SHA-256 必须与 `file.sha256` 一致；正文不得绕过工具静默修改。
3. 现行 AI 资料必须有人工核验记录。
4. 任一修订发生后，旧主文件先进入 `versions/`，当前修订号严格递增。
5. `supersedes` 与 `supersededBy` 必须双向指向。
6. 状态只能沿状态机合法转移，且每次转移写入历史。
7. 归档和替代都不物理删除正文。
8. `catalog.json` 与 `INDEX.md` 必须可由 `meta.json` 完全重建。
9. `related`、`supersedes` 和 `supersededBy` 不得指向不存在的资料。
10. 资料路径不得使用绝对路径或 `..` 越出条目目录。

## 5. 操作流程

### 5.1 新资料入库

1. 将生成结果保存为工作区普通文件。
2. 选择唯一主题、类型、资料域、负责人和初始状态。
3. 运行 `add`；工具生成 ID，复制正文，计算哈希，写元数据并重建索引。
4. 运行 `validate`；只接受 0 错误结果。
5. AI 资料进入 review，完成人工核验后才能转为 active。

### 5.2 修订

1. 将新正文另存为独立来源文件。
2. 运行 `revise`，填写操作人、修订说明以及必要的模型/Prompt 更新信息。
3. 工具保留旧版快照、递增修订号，并把状态退回 draft。
4. 重新执行评审，再转为 review/active。

### 5.3 替代

当新资料在主题层面替代旧资料，而不是同一资料的修订时：

1. 新资料先独立入库并完成 review，转为 active。
2. 运行 `supersede <旧ID> <新ID>`。
3. 旧资料转为 superseded，并保留双向关系。

### 5.4 归档

不再使用的资料通过 `status ... archived` 归档。归档不删除正文、历史或旧版本。当前版本不提供原位取消归档，避免绕过状态机恢复过期结论；确有需要时，应以新资料重新入库并引用旧 ID。

## 6. 评审与 AI 可追溯

AI 生成资料入库时必须记录：

- `origin`：`ai` 或 `mixed`；
- `generator`：工具名称；
- `modelVersion`：实际模型；未知时写 `not-recorded`；
- `promptRef`：Prompt、会话或任务编号；未保留时写 `not-recorded`；
- `sourceRefs`：一手任务书、代码路径或外部来源；
- `humanReview` 与 `reviewNotes`：谁核验、依据什么、接受了哪些未验证风险。

人工核验至少检查：关键事实是否有来源、路径和接口是否存在、计划与现状是否混写、验收是否可执行、未验证项是否显式列出。人工核验不代表系统自动证明了事实正确。

## 7. 安全、并发与失败降级

- 资料库默认位于本地仓库，不提供远程访问或权限隔离；任何能写工作区的人都能改文件。
- `validate` 会以警告形式提示疑似私钥、令牌或口令。警告不打印疑似秘密原文；发现后应停止提交并人工检查。
- 工具面向单机顺序操作，不对多人同时修改同一资料提供锁或合并；并发场景应先建立 Git 分支并在合并前运行校验。
- 来源文件超限、重复内容、目标目录存在、旧版本快照冲突、非法状态或断链时，命令必须显式失败，不静默覆盖。
- 索引缺失或损坏时运行 `rebuild`；正文损坏时从 Git 或 `versions/` 恢复，不得直接改哈希掩盖问题。
- 主文件写入与元数据写入不是跨文件数据库事务。若进程在两者之间崩溃，保留旧版快照与来源文件，运行 `validate` 后人工恢复。

## 9. 兼容与迁移

当前仓库此前只有根目录开发计划，没有旧资料库数据。首个受管资料通过复制方式导入，原 `DEVELOPMENT_PLAN.md` 保持不变。未来 schema 升级必须保留旧字段读取默认值，并在发布前提供 `schemaVersion` 迁移脚本；当前版本不自动迁移未知 schema。
